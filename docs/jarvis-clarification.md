# Trip clarification — 2026-10-15

Jarvis now pauses materially incomplete packing/planning requests for one short bundle of up to three focused questions: destination and expected dates/conditions, duration, and camping style when relevant. It does not fetch a forecast or infer current weather from a place name. The clarification uses no model call or inventory retrieval and creates no inventory changes.

Known details in the current trip's user messages are reused. A reply to the bundle resumes its original packing intent, including a bare destination such as “Yosemite”; later duration/condition corrections retain that destination. A clearly new packing request starts fresh rather than borrowing another trip's weather. Assistant prose is not parsed as verified trip facts. Exact location queries and explicit inventory edits keep their existing paths.

Users can answer what they know or request a “basic list”, “assume”, “skip”, or say they are unsure. After the bundle Jarvis proceeds with supplied facts and explicitly labeled provisional assumptions for unresolved details instead of repeating a questionnaire. Fully specified trips go directly to the grounded answer workflow. Destination/style recognition is deliberately conservative and English-language; ambiguous free-form replies are preserved for the model rather than treated as verified forecasts.

The provider receives the original trip intent, user-supplied details/revisions and labeled unknowns. It still uses bounded searches and final-answer/citation validation, distinguishes owned records from general suggested supplies, and cannot save inventory through packing. The existing four-model-turn/final-no-tools behavior, deadlines, retry limits, exclusions and personal-essential record checks remain. A network failure in the inline chat now passes conversation history to the local fallback rather than discarding clarification answers. A clarification is labeled “Trip questions”; a local fallback is honestly labeled search, not AI success.

Context summaries are bounded, and an already-valid model answer is never truncated to make room. If the combined context summary would exceed the 4000-character answer budget, it is rendered separately as a context notice. The existing chat history/request bounds remain; it is session conversation context, not durable trip storage.

Local regression coverage exercises vague request → question bundle → supplied trip details → grounded answer, known-detail reuse, subsequent corrections, new-trip separation, unknown/basic/assumption escapes, non-packing/edit bypass, inline reply/draft behavior and offline continuation. Earlier answer/retrieval/budget tests explicitly request a basic list to keep exercising those original seams; the new acceptance tests exercise the vague-request behavior. Historical opt-in reliability fixtures and their recorded results are not retroactively changed or claimed to test this clarification flow.

Independent QA records final checks and any bounded synthetic live tailoring sample in `design-qa.md`. A mock passing trip details to a provider is evidence of context plumbing, not proof of model answer quality. No private inventory, hosted accounts, database writes, migration, deployment, commit or push is part of this assignment.
